# manage-development

Ведёт разработку по готовым артефактам задачи до полного выполнения, успешной UI-проверки и актуализации Master-спецификации.

## Вход

Папка задачи `docs/NN_КраткоеНазвание/` с `spec.md` и `todo/todoN.md`. Если артефактов нет — остановись и предложи прогнать пайплайн с **prepare-intent**.

## Алгоритм

### 1. Понимание

1. Прочитай `intent.md` и `spec.md` целиком (дерево проекта, планы, тесты, граф зависимости).
2. Составь план выполнения: список todo в порядке графа, отметь, какие можно пускать параллельно.
3. Если детали кодовой базы неясны — сначала делегируй `explore` точечные вопросы (с требованием отвечать `файл:строка`).

### 2. Выполнение

Для каждого todo (по одному; параллельные — несколькими вызовами `task` в одном сообщении):

1. Прочитай `todo/todoN.md` целиком.
2. Делегируй субагенту, указанному в поле «Агент» (инструмент `task`, `subagent_type` = имя агента). В промпте передай:
   - полный путь к `todo/todoN.md` и `spec.md`;
   - точную формулировку подзадачи и критерий приёмки;
   - ссылки на файлы из spec (`файл:строка`);
   - напоминание прогонять свои тесты и включить их итоги в отчёт.
3. Получив отчёт, проверь критерий приёмки. Если субагент не прогнал тесты — верни подзадачу с требованием догнать.

### 3. Учёт (после КАЖДОГО todo)

Обнови `todo/todoN.md`:

- пометь статус: `☐ в работе` → `☑ выполнено` или `✗ ошибка`;
- заполни раздел «Результат выполнения»: статус, что сделано, итоги тестов.

Не изменяй исходные разделы (Контекст/Что сделать/Ограничения/Результат) — только статус и «Результат выполнения».

### 4. UI-приёмка и исправления

1. Когда все todo закрыты — из корня репозитория выполни `docker compose up -d --build`, чтобы пересобрать и перезапустить приложение в контейнерах. Только после этого запусти `ui-tester` (инструмент `task`, `subagent_type: ui-tester`) с описанием: какие фичи проверить, сценарии из spec.md «Тесты → UI», URL `http://localhost:8080`, вход `admin/admin123`. Не запускай API, frontend или БД отдельными процессами.
2. **pass** → проверь, что все todo закрыты, результаты обязательных тестов записаны, критерии приёмки spec подтверждены, блокирующих вопросов нет. Перейди к шагу 5.
3. **fail** → по найденным проблемам создай corrective-подзадачу(и) `todo/todo{M+1}.md` (агент — тот, чья часть упала), вернись к шагу 2. Цикл «исправление → ui-tester» повторяй до pass или до 3 итераций; после 3 итераций остановись и вынеси проблемы пользователю.

### 5. Обновление Master-спецификации (только после успешной приёмки)

1. После подтверждения всех условий шага 4 делегируй `master-spec-updater` (инструмент `task`, `subagent_type: master-spec-updater`).
2. Передай полный путь к папке задачи, `spec.md`, итоги закрытия todo, результат backend/frontend-тестов, вердикт `ui-tester: pass`, краткое описание принятой реализации и отклонения/ограничения, если они были.
3. Явно укажи субагенту прочитать `.opencode/skills/update-master-spec/SKILL.md`. Субагент обязан прочитать навык самостоятельно и сверить спецификацию/отчёты с кодом.
4. Получи отчёт субагента. Статус должен быть `обновлено` либо `без изменений` с объяснением. Если субагент сообщает о блокировке или расхождении — не заявляй об обновлении; разреши вопрос через corrective-процесс или вынеси его пользователю.
5. При `fail` от ui-tester, невыполненных todo, красных тестах или незакрытых блокирующих вопросах этот шаг не запускай.

### 6. Финальный отчёт

После шага 5 сформируй отчёт пользователю: что сделано по spec, список файлов, итоги backend/frontend-тестов, вердикт ui-tester и итог обновления Master-спецификации.

## Правила

- Сам код не пишешь — только чтение, делегирование и обновление `todo/todoN.md`.
- Одна подзадача — один субагент. Не смешивай backend и frontend в одном промпте.
- Если субагент сообщает о баге в чужой части — не чини его «вместе с ним», создай отдельную corrective-подзадачу соответствующему агенту.
- Если todo требует решения пользователя (нет ответа в spec.md «Решения/Вопросы») — останови ветку, пометь статус `☐ в работе / блок: вопрос`, и вынеси вопрос пользователю.
- В процессе держи пользователя в курсе: после каждого закрытого todo — короткая строка статуса.

## Формат финального отчёта

```
Задача {NN_Название}: ЗАВЕРШЕНА | ТРЕБУЕТ РЕШЕНИЯ

Todo: выполнено X из Y
Backend: {список изменений}, тесты: P/W
Frontend: {список изменений}, тесты: P/W
UI-тест: pass | fail ({детали})
Master-спецификация: обновлена | без изменений ({детали}) | заблокирована ({причина})
Открытые вопросы: {список | нет}
```
