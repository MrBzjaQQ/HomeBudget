# prepare-specification

Создаёт техническую спецификацию `spec.md` по уже написанному `intent.md`.

## Вход

Папка задачи `docs/NN_КраткоеНазвание/` с заполненным `intent.md`. Если `intent.md` нет — остановись и предложи сначала **prepare-intent**.

## Алгоритм

1. **Прочитай** `intent.md` (намерение, результат, ограничения, открытые вопросы) и корневые `BRIEF.md` (`BRIEF.md`, `backend/BRIEF.md`, `frontend/BRIEF.md`, `docs/BRIEF.md`).
2. **Разведка кодовой базы.** Для каждого места, где нужно понимать текущее устройство, делегируй субагенту `explore` (инструмент `task`, `subagent_type: explore`) точечные вопросы: «как сейчас реализовано X», «какие файлы относятся к Y», «как устроено Z» — с требованием отвечать ссылками `файл:строка`. Если задача мелкая и всё ясно из BRIEF.md — разведку можно пропустить.
3. **Собери `spec.md`** по шаблону ниже. Заполняй каждый раздел; для неприменимых пиши «—» (не удаляй разделы).
4. **Решения по открытым вопросам** из intent.md: если ответ очевиден из кода/ТЗ — реши и запиши в раздел «Решения». Если требуется решение пользователя — оставь вопрос в разделе «Вопросы» и явно отметь, что без ответа нельзя начинать разработку.

## Шаблон spec.md

```markdown
# Spec: {Краткое название задачи}

Ссылка на intent: `intent.md` в этой папке.

## 1. Что делать
Нумерованный список функциональных требований (FR-1, FR-2, …). Каждое требование — проверяемое утверждение о поведении системы.

## 2. Что НЕ делать
Анти-требования: явные границы (взяты из intent.md «не делаем» + новые, найденные в коде).

## 3. Ограничения
- Технические: стек, версии, JSON-контракт (camelCase, enum — строки ВЕРХНИМ регистром, ошибки {code, message, errors}), JWT, Clean Architecture-правила проекта.
- Производительность/доступность, если актуально.

## 4. Варианты реализации
2–3 варианта с плюсами/минусами каждого.

## 5. Решения
Выбранный вариант и обоснование (1 абзац). Сюда же — ответы на вопросы из intent.md.

## 6. Вопросы
Открытые вопросы, требующие ответа пользователя (или «нет»).

## 7. Дерево проекта (затрагиваемые места)
Дерево с пометками: [N] — новый файл, [M] — меняется, [R] — удаляется. Только затронутые узлы, с кратким комментарием к каждому.

## 8. Backend-план
- Новые/изменённые сущности, сервисы, DTO, контроллеры (пути).
- Изменения схемы БД + название миграции (если есть).
- Новые/изменённые API-эндпоинты (метод, путь, запрос, ответ).

## 9. Frontend-план
- Новые/изменённые компоненты/сервисы/маршруты (пути).
- Изменения UI: какие экраны, какие состояния (пустое, загрузка, ошибка).

## 10. Тесты
- Backend (xUnit): какие сценарии, какие файлы.
- Frontend (vitest): какие сценарии, какие файлы.
- UI (Playwright): ключевые сценарии для ручной/автопроверки.

## 11. Граф зависимости задач
Список задач T1..Tn с зависимостями (стрелками) и пометкой, что можно делать параллельно (backend/frontend/тесты).
```

## Правила

- Покрывает **обе** части: backend (Clean Architecture) и frontend (Angular). Если задача только с одной стороны — вторую помечай «—» и объясни почему.
- Пути файлов — точные, по реальной структуре проекта (проверь по BRIEF.md / explore).
- Не пиши код в spec — только описание. Формулировки — «что», а не «как» (кроме раздела «Решения», где допустимы технические детали выбранного варианта).
- Русский язык.
- Не изменяй код проекта на этом шаге — только чтение и запись `spec.md`.

## Следующий шаг

После записи `spec.md` сразу продолжай навыком **prepare-todo** (та же папка задачи). В финальном сообщении: путь к `spec.md`, выбранный вариант, список вопросов (если есть).
