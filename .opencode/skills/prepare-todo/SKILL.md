# prepare-todo

Разбивает `spec.md` на атомарные подзадачи для субагентов.

## Вход

Папка задачи `docs/NN_КраткоеНазвание/` с заполненным `spec.md`. Если `spec.md` нет — остановись и предложи сначала **prepare-specification**.

## Алгоритм

1. **Прочитай** `intent.md` и `spec.md` целиком (особенно разделы «Дерево проекта», «Backend-план», «Frontend-план», «Тесты», «Граф зависимости задач»).
2. **Разбей на подзадачи** по правилам ниже.
3. **Создай файлы** `docs/NN_КраткоеНазвание/todo/todoN.md` (N = 1, 2, 3, … в порядке выполнения; параллельные ветки нумеруешь подряд и помечаешь «Параллельно с: todoM»).

## Правила разбивки

**Ориентировочный размер подзадачи:** её должен выполнить один субагент (backend-developer, frontend-developer, backend-tests-writer, frontend-tests-writer) **за один прогон с контекстом ~65536 токенов без сжатия**. Практический ориентир:

- не более ~3–5 файлов изменений;
- объём описания подзадачи в файле — не более ~1–1.5 экрана (150–250 строк markdown);
- одна подзадача = одна единица изменения (одна сущность+сервис, один компонент, одна группа тестов).

Если логический кусок больше — дробь дальше (сначала backend-сущности/сервисы, потом контроллеры, потом frontend-сервисы, потом компоненты, потом тесты).

**Критерий атомарности:** подзадачу можно проверить независимо — есть конкретный ожидаемый результат и способ его проверить (тест/команда/наблюдение).

**Порядок:** по графу зависимости из spec.md. Слой за слоем: Domain → Application → Infrastructure → API → Frontend-core → Frontend-features → тесты. Независимые backend/frontend-подзадачи помечай как параллельные.

## Шаблон todoN.md

```markdown
# Todo N: {краткое имя подзадачи}

- Агент: {backend-developer | frontend-developer | backend-tests-writer | frontend-tests-writer}
- Зависит от: {todoM, todoK | нет}
- Параллельно с: {todoM | нет}
- Статус: ☐ в работе / ☐ выполнено / ☐ ошибка

## Контекст
Кратко: зачем эта подзадача, какие требования из spec.md реализует (FR-x), что уже сделано предыдущими todo (если есть).

## Что сделать
Нумерованный список конкретных действий с точными путями файлов:
1. Создать/изменить `{путь}` — {что именно}.
2. …

## Ограничения
- Правила, которые нельзя нарушить (контракт API, Clean Architecture, сигналы/zoneless, ID миграций не менять, …).

## Результат (критерий приёмки)
- [ ] Конкретно проверяемое состояние (файл существует с таким-то содержимым/методом, команда `...` возвращает `...`, тесты проходят).

## Результат выполнения
_(заполнит manage-development после выполнения)_
- Статус:
- Что сделано:
- Итоги тестов:
```

## Правила

- Пути — точные (по spec.md, проверенные по BRIEF.md).
- Не дублируй весь spec в каждый todo — только необходимый контекст + ссылки: «см. spec.md, раздел N».
- Тестовые подзадачи — отдельными todo (backend и frontend), со списком сценариев из spec.md «Тесты».
- Последний todo — «Финальная проверка»: прогон всех тестов обоих уровней + (опционально) `npm run build` — агент manager/ui-tester.
- Не изменяй код проекта на этом шаге — только чтение и запись файлов `todo/`.

## Следующий шаг

После создания `todo/todoN.md` заверши пайплайн подготовки: сообщи пользователю количество подзадач, порядок/параллелизм и предложи запустить **manage-development**.
