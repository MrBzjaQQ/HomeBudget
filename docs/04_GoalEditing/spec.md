# Spec: GoalEditing

Ссылка на intent: `intent.md` в этой папке.

## 1. Что делать

- **FR-1.** На странице «Финансовые цели» пользователь может открыть существующую цель в режиме редактирования.
- **FR-2.** В режиме редактирования пользователь может изменить все сохраняемые пользователем сведения цели: название, целевую сумму, связанный счёт накоплений и необязательную дату достижения. Форма изначально заполнена текущими значениями цели.
- **FR-3.** При сохранении сервер валидирует изменённые сведения по тем же бизнес-правилам, что и при создании цели: название после удаления пробелов обязательно и не длиннее 100 символов; целевая сумма больше нуля и не превышает `Validation.MaxAmount`; связанный счёт существует; дата либо отсутствует, либо имеет формат `yyyy-MM-dd`.
- **FR-4.** После успешного изменения список обновляется данными сервера, пользователь получает уведомление об успехе, форма редактирования закрывается. При ошибке сохранения пользователь получает сообщение API; форма остаётся доступна.
- **FR-5.** Пользователь может отменить редактирование без сохранения; значения черновика сбрасываются, цель остаётся неизменённой.
- **FR-6.** Изменение связанного счёта или параметров цели не меняет записи накоплений. Рассчитанные значения «накоплено», прогресс, достижение и ежемесячная норма продолжают вычисляться существующей серверной логикой с учётом текущих параметров цели и выбранного счёта.
- **FR-7.** Редактирование доступно только на странице «Финансовые цели» (`/goals`). Страница «Аналитика» (`/stats`) остаётся только для чтения: на ней нет кнопки/формы редактирования и она не вызывает операцию обновления цели.
- **FR-8.** Обновление несуществующей цели завершается ответом 404 в согласованном формате API. Неавторизованный запрос не выполняет обновление.

## 2. Что НЕ делать

- Не добавлять редактирование, создание или удаление целей в разделе аналитики.
- Не делать редактируемыми вычисляемые сведения: накопленную сумму, месячную норму, прогресс, статус достижения, имя/цвет счёта в представлении или дату создания.
- Не менять правила расчёта накопленного, прогресса, достижения и ежемесячной нормы.
- Не менять сценарии создания и удаления целей, за исключением необходимого переиспользования полей формы без регрессий.
- Не менять и не удалять записи накоплений при редактировании цели.
- Не добавлять поля, таблицы или миграции БД: редактируются существующие атрибуты финансовой цели.

## 3. Ограничения

- Стек: Angular 22 (signals, zoneless, standalone, Tailwind 4), ASP.NET Core 10, Clean Architecture, PostgreSQL 16; frontend-тесты — vitest, backend — xUnit.
- Контроллеры используют `IGoalsService`, не обращаются к `DbContext`; доступ к данным — через `IUnitOfWork`.
- JSON использует camelCase. Ошибки в формате `{code, message, errors}`; валидация — 400 `ValidationFailed`, отсутствие цели — 404 `NotFound`, авторизация — 401.
- API цели доступно только авторизованным пользователям. Существующая область видимости целей остаётся общей для семьи.
- Суммы положительные, не выше `Validation.MaxAmount`; дата передаётся строкой `yyyy-MM-dd` или `null`.
- Не менять существующие идентификаторы миграций. Новая миграция не требуется.
- Для времени/данных фронтенд использует существующие модели, сервисы, сигналы и отображение ошибок `ApiError`/`ToastService`.

## 4. Варианты реализации

**Вариант A. Полное обновление через PUT и отдельный режим редактирования в текущей форме страницы целей.**
+ Явный контракт полного набора изменяемых полей, соответствующий форме редактирования; валидацию можно согласовать с созданием.
+ Сохраняет одну форму и понятное разделение режима добавления/редактирования.
- Требуется отдельный запросный DTO/метод API обновления и аккуратное управление состоянием формы.

**Вариант B. Частичное обновление через PATCH с передачей только изменённых полей.**
+ Клиент может отправлять только изменившиеся поля.
- Добавляет сложность частичного обновления nullable-даты и валидации составного состояния без продуктовой необходимости: текущая форма позволяет редактировать весь набор полей.

**Вариант C. Удалить цель и создать её заново с новыми значениями.**
+ Не требует операции обновления.
- Меняет идентификатор/дату создания, несёт риск случайного удаления цели, хуже для пользователя и не соответствует ожидаемому редактированию.

## 5. Решения

Выбран **Вариант A**: авторизованный `PUT /api/goals/{id:int}` принимает полный набор редактируемых полей `name`, `targetAmount`, `containerId`, `dueDate` и возвращает обновлённый `GoalDto`. Frontend предоставляет в списке целей на `/goals` действие «Редактировать», открывающее существующую форму с заполненными значениями; режим формы различается от создания и вызывает соответствующую операцию. PUT выбран вместо PATCH, поскольку форма редактирует цель целиком, а обязательность полного набора полей исключает неоднозначность обновления даты и счёта.

Открытый вопрос из `intent.md` решён по исходному ТЗ финансовых целей (`docs/02_FinancialGoals/ТЗ_Финансовые_цели.md`) и действующей модели: пользовательские сохраняемые поля — название, целевая сумма, счёт накоплений, дата достижения. Эти же поля уже составляют форму создания (`frontend/src/app/features/goals/goals.component.html:17-64`), DTO запроса (`backend/Budget.Application/Goals/GoalsDtos.cs:3-9`) и сущность цели (`backend/Budget.Domain/Entities/FinancialGoal.cs:5-17`). Вычисляемые атрибуты не редактируются.

Для PUT применяется существующая серверная логика проверки полей создания, затем сохраняется существующая цель. Повторное построение `GoalDto` сохраняет серверное вычисление накоплений, месячной нормы и признака достижения. При смене счёта накопленное значение соответствует новому связанному счёту; записи обоих счетов остаются нетронутыми. В аналитике не добавляются управляющие элементы или вызовы обновления — текущая визуализация прогресса остаётся read-only.

## 7. Дерево проекта (затрагиваемые места)

```
backend/
├── Budget.Application/Goals/
│   ├── GoalsDtos.cs                 [M] запрос обновления цели
│   ├── IGoalsService.cs             [M] контракт обновления
│   └── GoalsService.cs              [M] поиск, валидация, изменение и возврат DTO
├── BudgetApi/Controllers/
│   └── GoalsController.cs           [M] авторизованный PUT /api/goals/{id:int}
└── BudgetApi.Tests/
    └── GoalsTests.cs                [M] интеграционные сценарии обновления

frontend/src/app/
├── core/
│   ├── models.ts                    [M] тип payload полного обновления
│   └── goals.service.ts             [M] PUT-операция GoalsService
└── features/goals/
    ├── goals.component.ts           [M] управление режимами формы и сохранением
    ├── goals.component.html         [M] действие редактирования и заполненная форма
    └── goals.component.spec.ts      [M] проверка UI-сценариев изменения
```

`frontend/src/app/features/stats/` не меняется: существующий экран аналитики уже показывает цели без действий изменения (`stats.component.html:118-159`). Схема БД, доменная сущность, миграции, маршруты и навигация не меняются.

## 8. Backend-план

- Изменить `Budget.Application/Goals/GoalsDtos.cs`: определить тип запроса обновления с обязательными полями `name`, `targetAmount`, `containerId` и nullable/необязательной `dueDate` в формате `yyyy-MM-dd`. DTO ответа остаётся без изменений.
- Изменить `Budget.Application/Goals/IGoalsService.cs`: добавить метод обновления цели по `id`.
- Изменить `Budget.Application/Goals/GoalsService.cs`: найти цель (404 при отсутствии), выполнить правила валидации, существующую проверку счета и даты, обновить четыре пользовательских поля, сохранить через `IUnitOfWork`, заново построить и вернуть `GoalDto`. Не изменять вычисления списка/DTO.
- Изменить `BudgetApi/Controllers/GoalsController.cs`: добавить `PUT /api/goals/{id:int}`, принять тело запроса, вызвать Application-сервис и вернуть 200 с обновлённым `GoalDto`. Контроллер остаётся `[Authorize]`.
- Миграция/изменение схемы БД: нет.
- API-контракт:

| Метод | Путь | Запрос | Ответ |
| --- | --- | --- | --- |
| PUT | `/api/goals/{id:int}` | `{ "name": "Отпуск", "targetAmount": 150000, "containerId": 1, "dueDate": "2026-12-31" }`; `dueDate` может быть `null` | 200 — пересчитанный `GoalDto`; 400 — ошибки валидации; 404 — цель не найдена; 401 — нет авторизации |

**Backend xUnit — `backend/BudgetApi.Tests/GoalsTests.cs`:** валидный PUT обновляет все пользовательские поля и возвращает ожидаемый DTO; GET подтверждает сохранение; смена счёта корректно меняет источник `saved` при сохранении исходных записей; очистка dueDate и валидная дата; проверки пустого/слишком длинного имени, нулевой/отрицательной/превышающей лимит суммы, несуществующего счёта и неверной даты; несуществующая цель даёт 404; неавторизованный PUT даёт 401. Также проверить, что исходные записи накоплений не изменились.

## 9. Frontend-план

- Изменить `frontend/src/app/core/models.ts`: добавить тип payload обновления цели с теми же полями, что и payload создания.
- Изменить `frontend/src/app/core/goals.service.ts`: добавить `updateGoal(id, payload)` для `PUT /api/goals/{id}`; существующие list/create/delete оставить без изменения контракта.
- Изменить `frontend/src/app/features/goals/goals.component.ts`:
  - хранить id текущей редактируемой цели либо отдельный режим формы;
  - при начале редактирования заполнить черновики названием, суммой, id счёта и датой;
  - сохранить существующую клиентскую валидацию, различать add/update, показывать соответствующие toast-сообщения, после успеха закрыть форму и перезагрузить список;
  - при отмене очистить черновики и сбросить режим редактирования;
  - обработать ошибки обновления по сообщению `ApiError.from(err).message`, сохранив форму открытой.
- Изменить `frontend/src/app/features/goals/goals.component.html`: на карточке цели добавить действие «Редактировать»; при редактировании показывать уже существующую форму с текущими значениями и кнопками сохранения/отмены, не допуская неоднозначности с режимом добавления. Существующее удаление и просмотр оставить.
- Состояния загрузки/пустого списка/ошибки сохраняются. Если счета накоплений отсутствуют, действуют прежние ограничения создания; форма редактирования остаётся доступной с текущим счётом, а новые значения счёта выбираются из доступного списка. Ошибка загрузки счетов не должна позволять отправить некорректный запрос.
- `stats.component.ts/html` остаются read-only и не получают метод обновления.

**Frontend vitest — `frontend/src/app/features/goals/goals.component.spec.ts`:** открыть редактирование и проверить заполненные данные; отправить полный payload обновления; успешное обновление закрывает форму, показывает успех и перечитывает список; отмена не вызывает update; клиентские ошибки не вызывают update; ошибка API показывает сообщение и оставляет редактирование доступным; создать/удалить цель можно как прежде. Проверить отсутствие действий изменения в компоненте аналитики (существующие тесты stats не должны регрессировать).

## 10. Тесты

- **Backend:** `backend/BudgetApi.Tests/GoalsTests.cs` — перечисленные сценарии PUT, проверки авторизации/валидации/404 и неизменности записей накоплений. Выполнить полный набор `dotnet test` из `backend/BudgetApi.Tests`.
- **Frontend:** `frontend/src/app/features/goals/goals.component.spec.ts` — поведение формы и API; выполнить полный набор `npx ng test` из `frontend`.
- **UI (Playwright):** на `/goals` отредактировать название, сумму, счёт и дату и убедиться, что после обновления видны новые значения и корректный рассчитанный прогресс; отменить изменение и убедиться, что данные не изменились; проверить ошибки валидации/API и сохранение текущих сценариев создания/удаления. На `/stats` проверить, что прогресс целей виден, но кнопок/форм редактирования нет и экран аналитики продолжает работать.

## 11. Граф зависимости задач

```
T1 (backend): DTO, IGoalsService, GoalsService, PUT GoalsController
T2 (backend tests): тесты PUT в GoalsTests.cs, dotnet test     ← T1

T3 (frontend): модели, GoalsService, форма редактирования на /goals
T4 (frontend tests): тесты формы/update, npx ng test           ← T3

T5 (UI): проверить /goals и read-only /stats                   ← T2, T4
```

Backend-цепочка T1 → T2 и frontend-цепочка T3 → T4 независимы, их можно выполнять параллельно. UI-проверка T5 выполняется после зелёных backend- и frontend-тестов.
