# Master-спецификация: «Домашний бюджет»

> Единая актуальная спецификация поведения продукта. Документ описывает функциональность, уже принятую в основную версию приложения. Подробности разработки конкретной фичи и критерии её приёмки остаются в соответствующей спецификации задачи.

## 1. Назначение и границы продукта

«Домашний бюджет» — веб-приложение для семейного учёта финансов, используемое в домашней сети небольшой семьёй (обычно 2–3 человека). Приложение помогает вести доходы и расходы, планировать расходы, отслеживать накопления и финансовые цели, анализировать данные и выгружать операции в Excel.

- Основной язык интерфейса — русский; валюта — RUB.
- Все авторизованные аккаунты равноправны; роли и публичная регистрация отсутствуют.
- Пользователи и категории операций указывают автора и классификацию данных, а не ограничивают их видимость: финансовые данные доступны семье.
- В приложении нет банковской интеграции, автоматического импорта или конвертации валют.

## 2. Пользователи, доступ и безопасность

- Вход выполняется по логину и паролю. API выдаёт JWT сроком на 24 часа; пароли хранятся в виде BCrypt-хэшей.
- Первый аккаунт `admin` создаётся сидером. Создание новых аккаунтов доступно авторизованным пользователям внутри приложения; регистрации извне нет.
- Пользователь может менять пароль, отображаемое имя, а также активировать и деактивировать аккаунты семьи.
- Деактивированный аккаунт не может войти, но остаётся в исторических операциях и доступен для атрибуции истории.
- Любой вошедший пользователь видит и может вести общие семейные данные; записи не изолированы по владельцу.
- Администратор `admin` исключён из списка участников и агрегатов накоплений, но может вносить накопления за другого участника.
- Приложение предназначено для домашней сети; сетевое развёртывание не должно открывать сервис в публичный интернет.

## 3. Функциональность

### 3.1. Журнал операций — `/`

- Доходы и расходы создаются, редактируются и удаляются с подтверждением удаления.
- Операция содержит вид, положительную сумму, дату, категорию, пользователя-автора и необязательный комментарий до 500 символов.
- Тип операции должен соответствовать типу категории. Дата операции не может быть позже сегодняшней даты по серверному времени.
- Журнал по умолчанию показывает выбранный месяц и поддерживает период, пользователя, вид, категории, поиск по комментарию и сортировку по дате/сумме.
- Список постраничный; панель итогов показывает доходы, расходы и чистый остаток с учётом выбранного периода и фильтров.
- Архивные категории остаются в истории, но не предлагаются для новых операций.

### 3.2. Категории — `/categories`

- Категории имеют ровно два уровня: группа и необязательная подкатегория. Тип `INCOME`/`EXPENSE` задаётся группой и наследуется подкатегорией.
- Поддерживаются создание, изменение названия/цвета/порядка сортировки, архивирование и восстановление.
- Имя уникально в пределах типа и родительской категории.
- Категорию, на которую ссылаются операции или позиции планового бюджета, нельзя физически удалить; для сохранения истории используется архив.

### 3.3. Аналитика — `/stats`

- Аналитика семейная и не фильтруется по автору операции.
- Отображаются расходы по категориям за месяц, топ категорий и динамика доходов/расходов за скользящие 12 месяцев.
- Окно динамики заканчивается выбранным месяцем, но не позже текущего серверного месяца.
- Блок «План по категориям» показывает план, фактические расходы и разницу для категорий, имеющих план или расходы. Разница равна `план − факт`; превышение плана выделяется как отрицательное значение.
- Блок «Накопления за 12 месяцев» показывает баланс накоплений по месяцам, изменение относительно предыдущего месяца и суммы по членам семьи; администратор исключён.
- Блок «Прогресс финансовых целей» доступен только для просмотра. Он показывает название цели, сумму накоплений относительно целевой суммы, процент (не более 100%) и статус достижения. Загрузка, пустой список и ошибка запроса имеют отдельные состояния.
- Ошибки одного дополнительного блока не должны маскироваться под пустые данные или ломать остальные показатели аналитики.

### 3.4. Плановый бюджет — `/budget`

- Для любого прошлого, текущего или будущего месяца можно вести любое количество позиций расходов; в одной категории за месяц разрешено несколько позиций.
- Позиция содержит месяц, расходную категорию, положительную сумму и необязательный комментарий до 500 символов.
- Страница группирует позиции по категориям и показывает план, фактические расходы семьи и разницу. Фактические расходы включают все аккаунты.
- Категории с расходами без заданного плана также отображаются с планом 0 и отрицательной разницей. Категории без плана и расходов не показываются.
- Позиции можно создавать, редактировать (включая перенос между месяцами) и удалять с подтверждением.
- Категорию с позициями бюджета нельзя физически удалить.
- Экспорт планового бюджета в Excel не входит в функциональность.

### 3.5. Накопления — `/savings`

- Семья управляет общим списком счетов накоплений с названием и цветом.
- Для каждого месяца ведутся независимые балансы по паре «счёт + член семьи»; автоматического переноса из прошлого месяца нет.
- У одного участника может быть не более одной записи для одного счёта за один месяц. Запись можно создать, изменить (в том числе перенести между месяцами, счетами и участниками) и удалить.
- Суммы — положительные; записи за админа запрещены. В месячном итоге отображаются записи всех членов семьи и сумма балансов.
- Счёт с записями накоплений или привязанными финансовыми целями удалить нельзя.
- Аналитика показывает скользящее окно 12 месяцев, не включая будущие месяцы; отрицательная дельта отображается вниз/красным.
- Для целей используется баланс выбранного счёта за последний месяц с данными, не позже текущего серверного месяца.
- Экспорт накоплений в Excel не входит в функциональность.

### 3.6. Финансовые цели — `/goals`

- Семья может создать, просматривать, редактировать и удалить финансовые цели. Цели общие для семьи.
- Цель содержит название (до 100 символов), целевую положительную сумму, связанный счёт накоплений и необязательную дату достижения.
- На странице отображаются накопленная сумма, прогресс с ограничением 100%, дата достижения, если задана, и рассчитанная ежемесячная норма, если цель не достигнута и срок не прошёл.
- Цель достигнута, когда накоплено не меньше целевой суммы. Ежемесячная норма округляется вверх до целого рубля и не показывается для достигнутой цели, цели без срока или прошедшего срока.
- Редактирование доступно только на `/goals`. Карточка прогресса на `/stats` остаётся read-only.
- Удаление цели не изменяет счёт или записи накоплений. Удалить счёт, привязанный к цели, нельзя.

### 3.7. Экспорт — `/export`

- Экспорт операций формируется сервером в формате `.xlsx` за месяц или год с фильтром по семье/конкретному пользователю.
- Месячный файл содержит операции и сводку расходов по категориям.
- Годовой файл содержит 12 месячных листов и лист «Сводка»; пустые месяцы включаются.
- Суммы в файле должны соответствовать данным приложения; экспорт включает архивные категории и сохранённую атрибуцию автора операции.

### 3.8. Настройки и навигация

- Раздел настроек содержит смену пароля и управление аккаунтами семьи.
- Основные разделы доступны через навигацию; на узких экранах дополнительные разделы доступны через «Ещё».
- Мобильная нижняя навигация сохраняет пять ячеек.
- Интерфейс адаптивен для телефона и не требует горизонтальной прокрутки для основных сценариев.

## 4. Данные и общие правила

- Денежные значения хранятся как `DECIMAL(15,2)`/`numeric(15,2)`. Операции и плановые суммы положительны; смысл знака определяется видом операции или разницей план/факт.
- Лимит суммы — `999 999 999 999.99`.
- Даты операций передаются как `yyyy-MM-dd`; месяц бюджета и накоплений в API передаётся как `yyyy-MM`.
- JSON использует `camelCase`; перечисления сериализуются строками верхнего регистра, например `EXPENSE`.
- Ошибки API имеют форму `{ "code": "...", "message": "...", "errors": { ... } }`. Типичные коды: `ValidationFailed`, `Unauthorized`, `NotFound`, `Conflict`, `InternalServerError`.
- Удаление сущностей, на которые ссылается финансовая история, блокируется понятной ошибкой конфликта; связанные данные не удаляются каскадно.

## 5. Карта API по областям

Все API-маршруты требуют авторизации, кроме входа.

| Область | Основные маршруты |
| --- | --- |
| Авторизация | `POST /api/auth/login`, `GET /api/auth/me` |
| Пользователи | `GET/POST /api/users`, `PUT /api/users/{id}` |
| Операции | `GET/POST /api/transactions`, `PUT/DELETE /api/transactions/{id}`, `GET /api/transactions/summary` |
| Категории | `GET/POST /api/categories`, `PUT/DELETE /api/categories/{id}` |
| Бюджет | `GET /api/budget?month=yyyy-MM`, `POST /api/budget`, `PUT/DELETE /api/budget/{id}` |
| Накопления | `GET /api/savings/containers`, CRUD `/api/savings/containers/{id}`, `GET /api/savings?month=yyyy-MM`, CRUD `/api/savings/{id}`, `GET /api/savings/summary` |
| Цели | `GET/POST /api/goals`, `PUT/DELETE /api/goals/{id}` |
| Экспорт | `GET /api/export/month?year=...&month=...&userId=...`, `GET /api/export/year?year=...&userId=...` |

Точные поля запросов/ответов и коды конкретных операций описаны в исходных спецификациях фич, перечисленных ниже.

## 6. Технический контекст

- Frontend: Angular 22, TypeScript strict, standalone-компоненты, signals, zoneless change detection, Tailwind CSS 4, Chart.js; компонентные тесты — vitest.
- Backend: ASP.NET Core 10 Web API, Clean Architecture, EF Core 10; интеграционные тесты — xUnit.
- Слои backend: `Budget.Domain` → `Budget.Application` → `Budget.Infrastructure` → `BudgetApi`; контроллеры работают через Application-сервисы, без прямого доступа к `DbContext`.
- Хранилище: PostgreSQL 16, имена столбцов snake_case. Миграции EF Core находятся в `backend/Budget.Infrastructure` и применяются при старте API.
- Разработка: frontend `http://localhost:4200`, прокси `/api` на API `http://localhost:5080`.
- Продакшен: Docker Compose, API также раздаёт собранный SPA; адрес приложения в локальной сети обычно `http://localhost:8080`.

## 8. Правило актуализации Master-спецификации

После завершения разработки по папке задачи менеджер обновляет эту спецификацию только после того, как:

1. Все todo выполнены, проверки уровня backend/frontend зелёные.
2. UI-тестировщик завершил проверку с вердиктом `pass`.
3. Менеджер подтвердил выполнение критериев приёмки и отсутствие открытых блокирующих вопросов.

Затем менеджер делегирует обновление субагенту `master-spec-updater`. Тот обязан прочитать навык `.opencode/skills/update-master-spec/SKILL.md`, сверить завершённую `spec.md`, отчёт UI-тестировщика и фактический код, внести в Master только подтверждённое актуальное поведение и вернуть список изменений. Исторические ТЗ и другие задачи не переписываются. При неуспешном UI-тесте или незакрытых todo Master не обновляется.
