# ТЗ: Приложение «Домашний бюджет» (учёт доходов и расходов)

Версия: 1.1 (финальная по итогам Q1–Q5), сентябрь 2026. Статус: согласовано, можно начинать.

* * *

## 1. Общие сведения

| Параметр | Значение |
| --- | --- |
| Назначение | Единый семейный учёт доходов и расходов: внесение, просмотр, аналитика, экспорт в Excel |
| Пользователи | 2–3 члена семьи (общий семейный бюджет; пользователь нужен только для атрибуции — кто внёс операцию) |
| Роли | Нет (все аккаунты равны) |
| Развёртывание | Домашний сервер (Docker), доступ СТРОГО из домашней сети (Q5) |
| Валюта | RUB, одна валюта, без конвертаций |
| Ожидаемый объём данных | до ~5 000 операций/год, до ~50 категорий |
| Язык интерфейса | Русский. Код и комментарии — английский |

Цель: приложение, в которое удобно вносить 1–3 операции в день с телефона, видеть картину за месяц, и раз в год «выгрузить всё в Excel» для ревизии.

## 2. Функциональные требования

### FR-1. Пользователи и аутентификация

*   Пользователь: логин, отображаемое имя («Иван», «Мария»), пароль, is_active.
    
*   Вход по логину/паролю → JWT (срок жизни 24 ч). Выход — отброс токена.
    
*   Регистрация извне закрыта: аккаунты создаются изнутри (FR-1.1). Первый пользователь — seed.
    
*   Пароли: BCrypt. Смена пароля в настройках.
    
*   **Критерий приёмки:** неверный пароль → 401; деактивированный аккаунт не может залогиниться, история операций сохраняется.
    

### FR-1.1. Управление аккаунтами (без ролей)

*   Любой авторизованный пользователь может: добавить учётную запись (логин + отображаемое имя + пароль), переименовать, деактивировать/активировать.
    
*   Роли отсутствуют: все аккаунты имеют равные права (Q4).
    
*   Пользователь нужен только для определения, кто внёс доход или расход: отображается в «Кто» в журнале, в формах и в экспорте; операции не принадлежат пользователю по правам — видит/редактирует/удаляет любой авторизованный.
    
*   Деактивированный аккаунт: не может логиниться, но остаётся в списке «Кто» (в фильтрах и экспорте) — история не теряет автора.
    
*   **Критерий приёмки:** любой пользователь создаёт новый аккаунт; новый аккаунт сразу может логиниться и вносить операции.
    

### FR-2. Категории

*   Иерархия ровно 2 уровня: группа → подкатегория (parent_id). Разрешено работать и без подкатегорий (плоская структура).
    
*   У категории: тип (INCOME / EXPENSE) — тип задаётся у группы и наследуется подкатегориями; цвет (для UI/чартов), порядок сортировки, флаг is_archived.
    
*   Уникальность: имя уникально в рамках (тип, родитель).
    
*   Удаление категории с операциями запрещено → только архивация (из формы выбора исчезает, в истории и экспорте остаётся).
    
*   Seed-категории (начальный набор):
    *   Доходы: Зарплата, Подработка, Кэшбэк/возвраты, Подарки, Прочее
        
    *   Расходы: Продукты (Супермаркет, Фермерский, Рынок), ЖКХ и связи (Ипотека, Коммуналка, Интернет/телефон), Транспорт (Бензин, Такси, Проезд), Здоровье (Аптека, Врачи), Детям (Детское, Детский сад, Обучение), Дом (Ремонт, Мебель, Хозтовары), Рестораны и кафе, Одежда, Подарки, Развлечения, Прочее
        
*   **Критерий приёмки:** CRUD работает; подкатегория наследует тип; архивная категория не видна в форме, видна в истории.
    

### FR-3. Операции (доходы/расходы)

*   Одна операция = запись: тип (доход/расход), сумма > 0 (2 знака), дата, категория, кто, комментарий (до 500 симв., необязательно).
    
*   CRUD: создать, отредактировать, удалить (с подтверждением). Изменение любого поля обновляет updated_at.
    
*   Категория операции обязана совпадать по типу с типом операции.
    
*   Сумма хранится положительной; тип хранится в записи (не выводится из категории, чтобы история не менялась при реорганизации категорий).
    
*   Валидация: amount > 0 и ≤ 999 999 999 999.99; **дата не позднее сегодняшнего дня — будущие даты запрещены (Q3, не отменяется)**; обязательны тип, дата, сумма, категория.
    
*   **Критерий приёмки:** операции с невалидными полями (в т.ч. с датой в будущем) отклоняются с понятным сообщением; после удаления операции итоги месяца пересчитаны.
    

### FR-4. Журнал (главный экран)

*   Список операций за выбранный месяц по умолчанию.
    
*   Итоговая панель: Доходы / Расходы / Остаток (за период, по выбранным фильтрам).
    
*   Фильтры: период (месяц/произвольный), кто (все/конкретный), тип, категории (мультивыбор), поиск по комментарию.
    
*   Пагинация (50 на страницу) или бесконечная прокрутка — до 1 000 строк за месяц ответ < 1 с.
    
*   Сортировка: по дате (по умолчанию), по сумме.
    
*   **Критерий приёмки:** все фильтры комбинируются; итоги соответствуют данным списка; мобильный макет читается с телефона без горизонтальной прокрутки.
    

### FR-5. Аналитика (дашборд)

*   Круговая диаграмма расходов за месяц по категориям (группы верхнего уровня).
    
*   Динамика за 12 месяцев: столбцы доход/расход по месяцам. Окно — 12 месяцев, заканчивающееся выбранным месяцем, но не позже текущего месяца (будущие месяцы не показываются).
    
*   Топ-5 категорий месяца с суммой и долей.
    
*   **Критерий приёмки:** суммы в диаграмме совпадают с итогами журнала за тот же период.
    

### FR-6. Экспорт в Excel

*   Два вида файла (формат — раздел 5):
    1.  Месяц: `Бюджет_2026-09.xlsx` — 1 лист.
        
    2.  Год: `Бюджет_2026.xlsx` — **13 листов: 12 месяцев + «Сводка» (Q1)**.
        
*   Параметры экспорта: период + кто (вся семья или конкретный пользователь).
    
*   Экспорт формируется на сервере (ClosedXML), возвращается как файл по GET.
    
*   **Критерий приёмки:** файлы открываются в Excel без предупреждений; 13 листов в годовом (включая Сводку); пустые месяцы присутствуют со шапкой (Q2); суммы в файлах совпадают с итогами приложения.
    

## 3. Модель данных (PostgreSQL)

Одна общая таблица операций на все типы, всех пользователей:

```sql
CREATE TABLE users (
    id            SERIAL PRIMARY KEY,
    username      VARCHAR(50)  NOT NULL UNIQUE,
    display_name  VARCHAR(100) NOT NULL,
    password_hash VARCHAR(255) NOT NULL,
    is_active     BOOLEAN      NOT NULL DEFAULT TRUE,
    created_at    TIMESTAMP    NOT NULL DEFAULT now()
);

CREATE TABLE categories (
    id          SERIAL PRIMARY KEY,
    name        VARCHAR(100) NOT NULL,
    kind        VARCHAR(10)  NOT NULL CHECK (kind IN ('INCOME','EXPENSE')),
    parent_id   INT          REFERENCES categories(id) ON DELETE RESTRICT,
    color       VARCHAR(7),
    sort_order  INT          NOT NULL DEFAULT 0,
    is_archived BOOLEAN      NOT NULL DEFAULT FALSE,
    created_at  TIMESTAMP    NOT NULL DEFAULT now(),
    UNIQUE (name, kind, parent_id)
);

CREATE TABLE transactions (
    id               BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id          INT           NOT NULL REFERENCES users(id),
    category_id      INT           NOT NULL REFERENCES categories(id),
    kind             VARCHAR(10)   NOT NULL CHECK (kind IN ('INCOME','EXPENSE')),
    amount           NUMERIC(15,2) NOT NULL CHECK (amount > 0),
    transaction_date DATE          NOT NULL,
    note             VARCHAR(500),
    created_at       TIMESTAMP     NOT NULL DEFAULT now(),
    updated_at       TIMESTAMP     NOT NULL DEFAULT now()
);

CREATE INDEX idx_txn_date      ON transactions (transaction_date);
CREATE INDEX idx_txn_user_date ON transactions (user_id, transaction_date);
CREATE INDEX idx_txn_category  ON transactions (category_id);
```

Принципы:

*   История неизменяема «назад»: category_id и user_id — FK, пользователи/категории не удаляются физически (деактивация/архивация).
    
*   Агрегаты (итоги, диаграммы, сводка) считаются на лету SQL-запросами; отдельная таблица агрегатов не нужна при заявленном объёме.
    

## 4. Backend API (ASP.NET Core Web API)

### 4.1 Аутентификация

| Метод | Путь | Описание |
| --- | --- | --- |
| POST | /api/auth/login | `{username, password}` → `{token, user}` |
| GET | /api/auth/me | Текущий пользователь |

### 4.2 Операции

| Метод | Путь | Описание |
| --- | --- | --- |
| GET | /api/transactions | Список: `from, to, userId, categoryId, kind, q, page, pageSize, sort` → `{items[], total, totals:{income,expense,net}}` |
| POST | /api/transactions | Создание (валидация даты: ≤ сегодня) |
| PUT | /api/transactions/{id} | Редактирование |
| DELETE | /api/transactions/{id} | Удаление |
| GET | /api/transactions/summary | Агрегаты: `from, to, groupBy=category |

Пример запроса POST:

```json
{ "kind": "EXPENSE", "amount": 1250.50, "date": "2026-09-14",
  "categoryId": 12, "userId": 2, "note": "Продукты, Пятёрочка" }
```

### 4.3 Категории / пользователи

| Метод | Путь | Описание |
| --- | --- | --- |
| GET | /api/categories | Дерево (группа + подкатегории), фильтр `kind`, `includeArchived` |
| POST | /api/categories | Создание |
| PUT | /api/categories/{id} | Изменение (имя, цвет, порядок, архив) |
| DELETE | /api/categories/{id} | Только если нет операций (иначе — 409, предлагается архив) |
| GET | /api/users | Список (все авторизованные; включая неактивных) |
| POST | /api/users | Создание аккаунта (все авторизованные) |
| PUT | /api/users/{id} | Переименование, смена пароля, is_active (все авторизованные) |

Соглашения:

*   Ошибки — единый JSON `{ "code": "...", "message": "..." }` (400/401/404/409).
    
*   Все даты — `yyyy-MM-dd`; время внутри сервера — MSK.
    
*   Авторизация: JWT. Роли отсутствуют — доступ к эндпоинтам только по «авторизован/не авторизован».
    
*   Экспорт: один запрос к БД за период (год = 1 запрос на 12 месяцев), разбивка по месяцам и сборка листов на C#.
    

## 5. Формат Excel-файла (библиотека — ClosedXML)

### Общее

*   Расширение `.xlsx`, шапка заморожена (freeze panes).
    
*   Числа: формат `#,##0.00` (разделитель тысяч — пробел, 2 знака); даты: `дд.мм.гггг`.
    
*   Ширина колонок: № 5, Дата 12, Тип 10, Категория 26, Комментарий 40, Кто 15, суммы 14.
    

### Структура листа месяца

1.  Строка 1: заголовок `«Движения за сентябрь 2026»` (слитая, жирный, 14pt).
    
2.  Строка 2: параметры — `Период: 01.09.2026–30.09.2026`, `Кто: вся семья | Иван`.
    
3.  Строка 4 — шапка данных: `№ | Дата | Тип | Категория | Комментарий | Кто | Доход, ₽ | Расход, ₽`
    *   Категория = «Группа / Подкатегория» (если есть); одиночная группа — как есть.
        
    *   В столбцы «Доход» и «Расход» пишется сумма по типу (пустая ячейка для несуществующего типа) — удобно для сводных таблиц.
        
4.  Данные: по 1 строке на операцию, сортировка по дате возрастательно.
    
5.  Итоговый блок (после пустой строки):
    *   `Итого за период`, `Доходы: X`, `Расходы: Y`, `Остаток: X − Y` (остаток — жирным).
        
6.  Блок `Расходы по категориям`: `Категория | Сумма, ₽ | Доля, %` (только расходные, по убыванию суммы, итоговая строка). **Только в месячном файле** (в годовом дублировался бы 12 раз).
    

### Месячный файл

*   1 лист, имя = полное название месяца: `Сентябрь 2026`. Файл: `Бюджет_2026-09.xlsx`.
    

### Годовой файл (13 листов)

*   Листы 1–12: `Январь` … `Декабрь` (год — в строке 1 заголовка листа).
    
*   Формат листа — как у месячного, БЕЗ блока «Расходы по категориям» (он дублируется 12 раз); блоки итогов по месяцам остаются.
    
*   **Пустые месяцы: лист создаётся всегда — 12 листов, даже если данных нет (шапка + блоки итогов с нулями) (Q2: всегда).**
    
*   **Лист 13 —** `Сводка` **(Q1: да):**
    *   Строка 1: «Годовая сводка 2026».
        
    *   Таблица: `Месяц | Доходы, ₽ | Расходы, ₽ | Остаток за месяц, ₽ | Остаток накопительно, ₽` — 12 строк (Январь–Декабрь; пустые месяцы — нули).
        
    *   Накопительно = сумма остатков с января ПО ЭТОТ месяц (в рамках экспортируемого года; баланс предыдущего года в сводку не зачёркивается — оговорка строкой под таблицей: «накопительно — в пределах 2026 года»).
        
    *   Итоговая строка `Итого за 2026` — жирным.
        
*   Файл: `Бюджет_2026.xlsx`.
    

## 6. Frontend (Angular)

*   Angular ≥ 22, standalone-компоненты, signals; TypeScript strict.
    
*   HTTP-клиент с интерцептором JWT; 401 → редирект на /login.
    
*   UI: Material (или Tailwind + компонентная библиотека на выбор) + Chart.js (ng2-charts) для дашборда.
    
*   Адаптивность: мобильный-first (основной сценарий — телефон), desktop — расширенные таблицы.
    

### Экраны

| Путь | Назначение |
| --- | --- |
| /login | Логин/пароль |
| / | Журнал: панель итогов (доходы/расходы/остаток), переключатель месяца (←/→), фильтр «Кто», фильтры (тип, категории, поиск), список/таблица операций, кнопка «+» |
| /transactions/new, /edit | Форма: тумблер доход/расход → сумма (крупный инпут), дата (default = сегодня, максимум — сегодня), категория (дерево, сгруппировано по типу), кто, комментарий |
| /stats | Дашборд: пир расходов по категориям за месяц, динамика 12 мес, топ-5 |
| /categories | Дерево категорий, CRUD, архив/восстановление, смена цвета и порядка |
| /export | Выбор: месяц (месяц+год) или год (год), кто; кнопки скачивания; индикатор генерации |
| /settings | Профиль (смена пароля); Аккаунты: список, добавление (логин/имя/пароль), переименование, деактивация/активация — доступно всем |

UX-правила:

*   Быстрое добавление: форма открывается в тапе «+», категория запоминает последний выбор.
    
*   Удаление — с confirm.
    
*   Суммы везде с разделителем тысяч и знаком (доходы зелёные, расходы красные).
    

## 7. Нефункциональные требования

| Область | Требование |
| --- | --- |
| Производительность | Журнал 1 000 строк < 1 с; экспорт года (13 листов, ~3 000 строк) < 10 с |
| Безопасность | BCrypt для паролей; JWT 24 ч; доступ СТРОГО из домашней сети (Q5) — наружу порты не публикуются, reverse proxy/Tailscale не нужны |
| Надёжность | Резервная копия `pg_dump` ежедневно (cron) → папка на сервере + копирование в Nextcloud (есть на сервере); хранение 7 последних дампов |
| Логирование | Серверные логи в файл, ошибки API — структурированные |
| Масштабируемость | Расчёт на 1 узел, 2–3 пользователя; горизонтальное масштабирование не проектируется |

| Q1. Лист «Сводка» в годовом экспорте | **Да**: 13-й лист — 12 строк (доходы/расходы/остаток месяца/остаток накопительно) + «Итого за год» |
| Q2. Пустые месяцы в годовом | **Всегда**: 12 листов всегда, пустой месяц — лист с шапкой и нулевыми итогами |
| Q3. Будущие даты | **Не допускать**: дата операции ≤ сегодня, на сервере и в UI |
| Q4. Пользователи/роли | **Без ролей**: любой авторизованный добавляет/управляет аккаунтами; пользователь нужен только для атрибуции «кто внёс» |
| Q5. Доступ извне | **Строго локально**: порты не публикуются наружу, Tailscale не нужен |
