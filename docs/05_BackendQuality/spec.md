# Spec: BackendQuality

Ссылка на intent: `docs/05_BackendQuality/intent.md`.

## 1. Что делать

- **FR-1.** Разделить каждый DTO/record/class, объявленный в тематических файлах DTO слоя Application, на отдельный `.cs`-файл: один тип — один файл. Вспомогательный mapper `UserDtos` не считать DTO и оставить отдельным файлом.
- **FR-2.** Сделать каждый DTO-record `sealed`, если он не является базовым типом для другого record. Сохранить типы, свойства, nullability, JSON-поля и публичные сигнатуры.
- **FR-3.** Вынести настройки каждой из семи EF-сущностей (`User`, `Category`, `Transaction`, `BudgetItem`, `SavingsContainer`, `SavingsEntry`, `FinancialGoal`) из `BudgetDbContext.OnModelCreating` в отдельный класс `IEntityTypeConfiguration<TEntity>`. Автоматически применять конфигурации из сборки либо явно регистрировать все конфигурации. Сохранить имена индексов, ограничения, связи, значения по умолчанию, точность чисел и миграционную модель. Оставить в контексте логику `UpdatedAt` для изменяемых сущностей.
- **FR-4.** Провести аудит backend-кода и тестов, определить повторяющиеся или висящие строковые/числовые значения, которые имеют общее предметное значение, и вынести их в подходящие по слоям файлы констант. Использовать общие производственные значения непосредственно в тестах, где они относятся к проверяемому контракту; значения, предназначенные только для тестовой фикстуры, хранить централизованно в тестовом проекте. Не создавать общий файл для несвязанных литералов.
- **FR-5.** Удалить из design-time factory зашитую строку подключения и fallback. Использовать тот же ключ конфигурации `ConnectionStrings:Default`, что и runtime-приложение; если значение отсутствует или пустое, выбрасывать явное исключение с понятным сообщением. Не менять provider/runtime-поведение приложения.
- **FR-6.** Удалить из backend исходников и отслеживаемых файлов конфигурации зашитую строку подключения. Локальный и контейнерный запуск должны получать её извне; Docker Compose уже передаёт `ConnectionStrings__Default` из переменных окружения. Секреты не добавлять в исходники или тестовые константы.
- **FR-7.** Добавить полную русскоязычную XML-документацию ко всем публичным backend-типам, методам и свойствам в production-проектах, включая DTO, контракты, доменные сущности, API и инфраструктуру. Каждый документированный член должен иметь `summary`; методы и конструкторы должны описывать все параметры через `param`, результаты — через `returns`, при наличии generic-параметров — через `typeparam`. Документация должна описывать смысл и ограничения, а не только повторять имя. Настроить генерацию XML-документации в backend-проектах и устранить предупреждения об отсутствующих XML-документах в этих публичных API.
- **FR-8.** Привести все имена тестовых методов к одному шаблону `[Метод]_[Условие]_[Результат]`: действие/операция, сценарий, ожидаемый результат. При переименовании тестов сохранить содержимое, покрытие и атрибуты теорий.
- **FR-9.** Сборка всех backend-проектов и весь набор backend-тестов должны успешно завершаться. Собрать приложение Docker Compose и проверить его работу в контейнере на `http://localhost:8080`, не запуская API, frontend или базу отдельными процессами.
- **FR-10.** Рефакторинг не меняет пользовательское поведение, API-контракт, бизнес-правила, миграции и данные. Поддерживается текущая PostgreSQL-схема; миграции не создаются, пока проверка модели не выявит реального изменения схемы.

## 2. Что НЕ делать

- Не менять маршруты, HTTP-методы/статусы, JSON-контракт, бизнес-логику, правила валидации, содержимое Excel-экспорта и пользовательский интерфейс.
- Не менять имена сущностей, свойства DTO, enum-значения, идентификаторы/содержимое существующих миграций или структуру БД.
- Не добавлять внешние зависимости, если требуемая функциональность реализуется штатными средствами .NET/EF Core.
- Не помещать реальные секреты, пароли или подключения в константы, тестовые данные, tracked config или отчёты.
- Не переписывать frontend и не документировать XML-комментариями TypeScript: задача относится к backend и его C#-тестам.
- Не превращать каждый внутренний/локальный литерал (например, отдельный текст сообщения или тестовый ожидаемый фрагмент) в глобальную константу без повторного использования или предметного смысла.

## 3. Ограничения

- Текущий backend — пять проектов без solution-файла: Domain, Application, Infrastructure, BudgetApi и BudgetApi.Tests; target framework — `net10.0`.
- Слои Clean Architecture сохраняются: Domain не зависит от других слоёв; Application зависит от Domain; Infrastructure — от Application и Domain; API — от Application и Infrastructure. Контроллеры не получают DbContext.
- PostgreSQL 16, EF Core 10, Npgsql и snake_case-конвенция остаются действующими. InMemory используется существующими интеграционными тестами.
- Действующие JSON-договорённости: camelCase, enum-сериализация строками верхнего регистра, ошибки `{code, message, errors}`; frontend зависит от них.
- Connection string runtime имеет ключ `ConnectionStrings:Default`; Docker Compose передаёт значение через `ConnectionStrings__Default`. Design-time tools должны использовать то же имя настройки и явно прекращать создание контекста при её отсутствии.
- `BudgetDbContext.SaveChanges`/`SaveChangesAsync` проставляют `UpdatedAt` для Transaction, BudgetItem и SavingsEntry; перенос конфигурации не должен менять эту логику.
- Набор тестов — xUnit integration tests на WebApplicationFactory/InMemory; большинство проверок идут через HTTP. База для `dotnet test` не требуется.
- Для проверки контейнера нужны Docker Compose и корректно заданные `.env` параметры `POSTGRES_PASSWORD` и `JWT_KEY`; реальные секреты не сохранять в репозитории.

## 4. Варианты реализации

1. **Файловое разнесение с локальными константами по слоям (выбран).** DTO и EF-конфигурации получают отдельные файлы; общие значения располагаются рядом с владеющим ими слоем/тестовой фикстурой; XML-документация включается во всех backend-проектах. Плюсы: ясное владение, нет межслойных циклов, небольшие независимые изменения. Минусы: затрагивается много файлов и требуется внимательно сверить EF-модель.
2. **Единый глобальный файл констант и централизованный файл документации.** Плюсы: всё формально находится в одном месте. Минусы: смешивает значения разных слоёв, ухудшает зависимости и не решает задачу документации у самих членов; отклоняется.
3. **Точечная документация и частичное разнесение моделей.** Плюсы: быстрее. Минусы: не отвечает требованиям про все публичные свойства/методы и отдельный файл для каждого DTO/конфигурации; отклоняется.

## 5. Решения

Выбран вариант 1. Под «строками в коде и висящими константами» понимаются повторно используемые или предметно значимые литералы, выявленные аудитом, а не все строки/числа без исключения. Каждая константа должна принадлежать подходящему слою; тесты используют производственную константу только там, где проверяют именно этот контракт, а тестовые учётные данные/параметры фикстуры принадлежат тестовому проекту и не должны переносить секреты. XML-документация охватывает публичные типы и их API-члены всех четырёх production-проектов; для тестового проекта — публичные test-кейсы и публичные helper-типы/методы. Тестовые методы документируются на русском с `summary` и `param`, если параметризованы.

В design-time factory используется стандартная конфигурация `ConnectionStrings:Default` (включая переменную окружения `ConnectionStrings__Default`); отсутствие значения приводит к исключению до вызова `UseNpgsql`. Значение connection string удаляется из `appsettings.json`, поскольку оно зафиксировано в репозитории, даже несмотря на маскированный пароль; локальную настройку следует передать через переменную окружения/user-secrets, контейнер — через существующий Compose. Отдельная очистка JWT-конфигурации не добавляется в scope сверх необходимого для контейнерной проверки; Compose обязан получать `JWT_KEY` снаружи.

DTO-record, которые не являются базовыми для другого record, объявляются `sealed`. Все семь сущностей получают раздельные конфигурации; перенос не требует новой миграции, если snapshot/модель остаются эквивалентными. Имена интеграционных тестов приводятся к полному шаблону с учётом `[Theory]`-сценариев. Для Docker acceptance проверяются успешный запуск API и SPA, готовность/подключение к Postgres, вход seed-пользователем и доступность базового API/страницы; Docker-сборка не запускает отдельные процессы вне Compose.

## 6. Вопросы

Нет. Объём XML-документации определён как публичные члены всех production-проектов и публичные тестовые/helper-члены проекта тестов; фактические значения секретов при проверке предоставляет оператор через локальное окружение.

## 8. Backend-план

- **Application:** разнести DTO из `AuthDtos.cs`, `UserDtos.cs`, `CategoryDtos.cs`, `TransactionDtos.cs`, `BudgetDtos.cs`, `SavingsDtos.cs`, `GoalsDtos.cs`, `ExportModels.cs`; оставить `UserDtos` mapper отдельно. Проверить ссылки во всех сервисах, интерфейсах и API. Все не наследуемые DTO-record сделать `sealed`.
- **Infrastructure:** создать семь конфигураций в `Budget.Infrastructure/Data/Configurations/`; перенести из `BudgetDbContext.OnModelCreating` полные правила маппинга, оставить автоматическое обновление `UpdatedAt` и DbSet. Не менять текущую схему, порядок/семантику связей, ограничений и индексов.
- **Design-time:** обновить `DesignTimeDbContextFactory` для `ConnectionStrings:Default`; пустое/отсутствующее значение вызывает `InvalidOperationException` с указанием настройки и безопасным сообщением без печати секрета. Источник значения согласовать с runtime-конфигурацией .NET, включая environment variables.
- **Конфигурация:** удалить `ConnectionStrings:Default` из checked-in `appsettings.json`; Compose остаётся источником контейнерного значения. Проверить, что `.env` игнорируется Git. Никакие значения из `.env` не коммитить.
- **Константы:** аудитом выявить повторяемые значения (форматы дат/месяцев, коды/ключи конфигурации, фикстурные значения и т. п.); выбрать владельца по Clean Architecture. Не вводить зависимость Domain/Application от API/Infrastructure. Не переносить секреты в константы. Повторно используемые production-значения должны использоваться тестами, если тест проверяет данный контракт.
- **XML-doc:** проверить все публичные типы/члены в Domain, Application, Infrastructure, API и публичные test/helper-члены в Tests; комментарии и описания — русские, обязательны summary и описания каждого параметра. Включить генерацию документации, добиться сборки без CS1591 в целевой области.
- **Тестовые имена:** переименовать несоответствующие шаблону методы `*Tests.cs`, не меняя сценарии и тестовые данные; `[Theory]`-методы сохраняют параметры и данные InlineData/MemberData.
- **Схема БД/миграции:** изменений не планируется; существующие миграции неизменяемы. Проверить отсутствие изменений модели посредством `dotnet ef migrations has-pending-model-changes` из `backend/BudgetApi` с `--project ..\Budget.Infrastructure`, если доступно окружение.
- **API:** endpoint-ы и их запросы/ответы — без изменений (`—`).

## 9. Frontend-план

—. Frontend не меняется: задача касается внутренней структуры backend; пользовательские экраны и вызовы API сохраняются. UI участвует только в проверке совместимости готового контейнерного приложения.

## 10. Тесты

- **Backend unit/integration (xUnit):** полный набор из `backend/BudgetApi.Tests`; проверка текущих login, users, categories, transactions, budget, savings, goals, export сценариев без регрессий. Все тесты должны иметь имена `[Метод]_[Условие]_[Результат]`.
- Добавить/обновить проверки для `DesignTimeDbContextFactory`: connection string отсутствует/пустая — явное исключение; допустимая конфигурация — создаётся контекст без изменения provider-конвенций. Проверки должны избегать зависимости от реальной БД, если это возможно по устройству factory.
- Проверить DTO без регрессии типов и сериализуемого JSON-контракта существующими API-тестами; все тесты должны компилироваться после разнесения.
- Проверить полную сборку всех backend-проектов и отсутствие XML-doc warnings в целевых проектах; применить `dotnet test` из `backend/BudgetApi.Tests`.
- Проверить отсутствие ожидающих изменений EF-модели; тесты InMemory сами по себе не подтверждают реляционные ограничения.
- **Frontend (vitest):** не изменяется и не обязателен для каждого кода-рефакторинга; при приемке Docker проверить, что собранный SPA загружается и совместим с неизменённым API.
- **Docker/UI acceptance:** из корня репозитория выполнить `docker compose up -d --build` с локально заданными секретами. Убедиться, что контейнеры app и postgres healthy/работают; открыть `http://localhost:8080`, войти `admin/admin123`, проверить доступность главного экрана и хотя бы одного API-backed раздела (например, журнал или категории), а также отсутствие ошибок загрузки/авторизации. Не запускать процессы API, frontend или БД отдельно.

## 11. Граф зависимости задач

```text
T1 Аудит и план constants/XML/имён тестов
 ├── T2 Разнести DTO и сделать DTO-record sealed ──┐
 ├── T3 Разнести EF-конфигурации -----------------┤
 ├── T4 Убрать connection-string fallback и config ┤
 └── T5 Централизовать общие константы ------------┤
                                                  └── T6 XML-документация всех backend-проектов
T2 + T3 + T4 + T5 + T6 ──> T7 Согласовать/переименовать тесты и добавить factory-проверки
T7 ──> T8 Backend build, tests и проверка EF model diff
T8 ──> T9 Docker Compose build и UI-приёмка
```

T2–T5 можно выполнять параллельно после T1 при согласовании владельцев файлов; T6 также может идти параллельно отдельному файловому набору, но изменения одних C#-файлов должны быть согласованы с соответствующим разработчиком. T7 начинается после интерфейсов для factory/констант; T8 и T9 выполняются строго последовательно. Master-spec обновляется только после успешного UI `pass`.
